# DMARC & DKIM Troubleshooting Runbook

A reference for interpreting DMARC aggregate reports against this Stalwart
deployment and acting on the common failure patterns. Built from a real
investigation on `cloud-claude.com` in 2026-05.

## How to read a Google DMARC aggregate report

Google sends one XML report per UTC day to the address in your `_dmarc`
record's `rua=`. Each `<record>` block summarises one source IP plus
disposition. The columns that matter:

| Column | What it means |
|---|---|
| `source_ip` | Server that delivered the message to Google. |
| `count` | Number of messages from that source in the window. |
| `policy_evaluated.disposition` | What Google did. `none` = delivered normally, `quarantine` = sent to spam, `reject` = bounced. |
| `policy_evaluated.dkim` / `spf` | Did DKIM/SPF align with the `From:` header domain? |
| `auth_results.dkim` (per selector) | Per-signature pass/fail. A message can have multiple signatures. |
| `auth_results.spf` | SPF check on the envelope MAIL FROM. |

DMARC passes if **either** SPF or DKIM is aligned. A `disposition: none` on
a `spf: fail` record is healthy if DKIM aligned.

## Failure patterns and what to do

### Pattern A — `spf: fail`, `dkim: pass`, `disposition: none`, source IP belongs to a forwarder

**Diagnosis:** legitimate mail you sent that was forwarded by an intermediary
(Gmail, Outlook, mailing list). SPF naturally breaks on forwarding because the
forwarder's IP is not in your SPF record. DKIM survives the forward and
rescues DMARC alignment. **This is DMARC working correctly.**

How to recognise:
- `source_ip` is in a known forwarder's range (Google `2607:f8b0::/32`,
  Outlook `40.92.0.0/15`, etc.).
- DKIM with `domain = your-domain` passes.
- `disposition: none`.

**Action:** none. Do **not** add the forwarder's IPs to SPF — that would let
anyone on that infrastructure spoof your domain.

### Pattern B — `spf: fail`, `dkim: fail`, `disposition: quarantine|reject`

**Diagnosis:** spoofing, OR a legitimate sender you forgot about (a SaaS
sending on your behalf with no SPF/DKIM setup).

**Action:**
1. Look up the source IP (`whois`, `host -t PTR`).
2. If it's a service you use (Mailgun, Sendgrid, transactional provider),
   add it to SPF or set up SPF/DKIM delegation as the provider documents.
3. If unknown, leave DMARC strict — it's working.

### Pattern C — same domain, one DKIM selector passes, another fails

**Diagnosis:** one of your signing keys is broken — the private key on the
server doesn't match the public key in DNS, or the published key is malformed.

**Action:** see "Fixing a broken DKIM selector" below.

### Pattern D — `spf: fail`, `dkim: none`, source IP is your own server

**Diagnosis:** your server sent unsigned mail. Either DKIM signing isn't
configured for the sender's domain, or the message was generated by a path
that bypasses signing (some bounce/DSN paths).

**Action:** verify `auth.dkim.sign` covers the sender domain in Stalwart
config. Check the per-domain DKIM signature exists.

## Fixing a broken DKIM selector

If a selector is failing on every message but another selector for the same
domain passes, the broken one's key material is mismatched between server
and DNS. Two recovery options:

### Option 1 — Disable the broken selector (fastest)

If the working selector is doing the job, just stop signing with the broken
one. In Stalwart webadmin: **Settings → Signatures**. Delete the broken
signature entry. Stalwart will continue signing with the remaining
signature(s) on the domain.

You can leave the corresponding DNS TXT record in place (no harm), or
remove it for cleanliness.

### Option 2 — Regenerate the keypair

1. **Webadmin → Settings → Signatures → Add Signature.** Pick the same
   algorithm as the broken one. Stalwart generates a new private key and
   selector.
2. **Webadmin → Management → Domains → `<your-domain>` → DNS Records.**
   Copy the new TXT record value Stalwart shows for the selector.
3. **DNS provider:** publish the new TXT record under
   `<new-selector>._domainkey.<your-domain>`.
4. Wait for DNS propagation (a few minutes for low-TTL records).
5. Send a test message. Check `Authentication-Results` header at the
   receiver — the new selector should show `dkim=pass`.
6. Once confirmed, delete the broken selector entry from Stalwart and
   remove its old DNS TXT record.

## Why the redirect-to-Gmail Sieve script can change DMARC reporting

If you have a Sieve `redirect` rule sending mail to Gmail (or any external
service) and that account further forwards, you'll see source IPs in the
forwarder's range appear in Google's DMARC reports as if "your domain" sent
them — because the original `From:` header is preserved through the chain.
This is expected (Pattern A above). It is not a problem unless DKIM is also
failing.

## Where outbound DKIM is signed in the codebase

For maintainers: `crates/common/src/config/smtp/auth.rs` defines the signer
selection. The relevant config key is `auth.dkim.sign`, which evaluates per
sender to a list of signature IDs. Each signature ID resolves to keys in
`signature.<id>.private-key`, `signature.<id>.algorithm`, etc., set via the
DKIM management API at `POST /api/dkim` (see
`crates/http/src/management/dkim.rs`).

## Reference: example clean-vs-broken record

Healthy (your server, both auth methods pass):

```xml
<record>
  <row>
    <source_ip>5.78.187.44</source_ip>
    <count>2</count>
    <policy_evaluated>
      <disposition>none</disposition>
      <dkim>pass</dkim>
      <spf>pass</spf>
    </policy_evaluated>
  </row>
  <auth_results>
    <dkim><domain>example.com</domain><result>pass</result><selector>202604r</selector></dkim>
    <spf><domain>example.com</domain><result>pass</result></spf>
  </auth_results>
</record>
```

Forwarded (Pattern A — looks scary, is fine):

```xml
<record>
  <row>
    <source_ip>2607:f8b0:4864:20::645</source_ip>   <!-- Google -->
    <count>1</count>
    <policy_evaluated>
      <disposition>none</disposition>
      <dkim>pass</dkim>     <!-- DKIM survived the forward -->
      <spf>fail</spf>       <!-- SPF naturally broke -->
    </policy_evaluated>
  </row>
</record>
```

Broken selector (Pattern C — needs action):

```xml
<auth_results>
  <dkim><domain>example.com</domain><result>pass</result><selector>202604r</selector></dkim>
  <dkim><domain>example.com</domain><result>fail</result><selector>202604e</selector></dkim>
</auth_results>
```
